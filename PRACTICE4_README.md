# Practice4 — работа с сетью

В этой практике каталог и детали получают данные из iTunes Search API. Исходные Compose-экраны и нижняя навигация сохранены. Избранное и настройки остаются заглушками для следующих практик.

## Как применить архив

1. Перед началом Practice4 завершить PR/MR предыдущей практики и перенести её изменения в `master` или `dev`, как указано в задании.
2. От обновлённой основной ветки создать новую ветку, например `practice4-network`.
3. Распаковать архив **в корень своей папки проекта** — туда, где уже лежат `settings.gradle.kts`, `gradlew.bat` и папки `app`, `gradle`.
4. Согласиться на объединение папок и замену совпадающих файлов. В архиве нет внешней папки с названием проекта: пути начинаются сразу с `app/...`, `gradle/...` и файлов инструкции.
5. Открыть проект в Android Studio и выполнить Gradle Sync.
6. Запустить конфигурацию `app` на устройстве или эмуляторе с интернетом.

Удалять файлы вручную не требуется. Версии SDK, AGP, Gradle, Kotlin и Compose из присланного проекта не менялись. Если исходный проект собирался у тебя, настройки SDK/JDK нужно оставить прежними.

Полный список новых и изменённых файлов с путями от корня находится в `CHANGED_FILES_PRACTICE4.md`.

## Соответствие заданию

| Требование Practice4 | Реализация |
| --- | --- |
| Данные из выбранного API | iTunes `/search` и `/lookup`, реальный источник `NetworkTrackRepository` |
| Асинхронная загрузка | `suspend`-методы Retrofit, `viewModelScope.launch`, `withContext(Dispatchers.IO)` в репозитории |
| Сетевые библиотеки | Retrofit 3.0.0, Gson Converter, OkHttp 4.12.0, Kotlin Coroutines |
| Состояние загрузки | `StateFlow` в ViewModel, индикатор и надпись «Загрузка…» на обоих экранах |
| Обработка ошибок | Нет соединения, таймаут, HTTP-ошибка, HTTP 429, неправильный JSON/ответ, элемент не найден; кнопка «Повторить» |
| Сеть управляется во ViewModel | ViewModel запускает UseCase, UseCase обращается к контракту Repository; экраны вызывают callback-функции |
| Чистая архитектура | `domain` содержит модель, результат, ошибки, контракт Repository и UseCase; `data` — DTO, mapper, API и реализацию Repository; `ui` — состояние, ViewModel, экраны |
| Настраиваемый запрос | Строка пользователя передаётся в `@Query("term")`; ID карточки — в `@Query("id")` |

Доменный слой не импортирует Android, Compose, Retrofit, Gson или классы из `data`/`ui`.

## Как работает приложение

При открытии каталога автоматически выполняется поиск `Daft Punk`, если в сохранённом состоянии ещё нет другого запроса.

Чтобы найти другие треки:

1. Ввести название трека, исполнителя или альбома.
2. Нажать кнопку с лупой справа от поля или клавишу «Найти» на клавиатуре.
3. Дождаться результата. Набор текста сам по себе не отправляет запрос на каждую букву.

Список показывает результаты последнего отправленного запроса; над списком указаны его текст и количество найденных элементов. Пустой успешный ответ отображается как «Ничего не найдено», отдельно от сетевой ошибки. Пустую строку поиска UseCase отклоняет без обращения к API.

Кнопка обновления в заголовке повторяет последний отправленный запрос. Если во время загрузки отправить новый поиск, предыдущая корутина отменяется; старый ответ не заменяет новый результат.

При нажатии на карточку в навигацию передаётся только `trackId`. ViewModel деталей выполняет отдельный запрос `/lookup`, затем показывает данные. Ошибка деталей не блокирует кнопку «Назад».

Запрос в поле сохраняется через `SavedStateHandle`; состояние экрана остаётся во ViewModel при переключении вкладок и изменении конфигурации Activity. При восстановлении процесса данные снова запрашиваются из API.

Обложки используют локальное оформление из Practice3. Названия, исполнители и информация в списке/деталях теперь приходят из API. Прослушивание, полноценное избранное и настройки не добавлялись, поскольку Practice4 этого не требует.

## Примеры запросов

Поиск по строке пользователя:

```text
GET https://itunes.apple.com/search?term=Daft%20Punk&limit=25&media=music&country=US
```

Загрузка выбранного элемента:

```text
GET https://itunes.apple.com/lookup?id=697195462&country=US
```

Параметры кодирует Retrofit; пробелы, кириллицу, `&` и другие символы не нужно вручную вставлять в URL. Для поиска и деталей используется один каталог `US`. Ключ API и регистрация для этих запросов не требуются.

DTO допускают отсутствие полей. Mapper пропускает неподдерживаемые и неполные элементы; повторяющиеся ID убираются до передачи в `LazyColumn`. Некорректная структура ответа отображается как ошибка. На ошибке API приложение не подставляет моковые данные.

## Основные файлы

Все пути ниже начинаются от корня проекта. Общая папка Kotlin-исходников: `app/src/main/java/com/example/itunes_search/`.

| Путь внутри общей папки | Назначение |
| --- | --- |
| `domain/model/Track.kt` | Модель, которую используют экраны |
| `domain/model/TrackResult.kt`, `TrackError.kt` | Результат операции и типы ошибок |
| `domain/repository/TrackRepository.kt` | Асинхронный контракт доступа к данным |
| `domain/usecase/SearchTracksUseCase.kt` | Проверка строки и запуск поиска |
| `domain/usecase/GetTrackDetailsUseCase.kt` | Проверка ID и получение деталей |
| `data/model/Track.kt`, `ItunesResponse.kt` | DTO ответа iTunes |
| `data/mapper/TrackMapper.kt` | Преобразование DTO в доменную модель |
| `data/remote/ItunesApi.kt` | Retrofit-методы с query-параметрами |
| `data/remote/NetworkModule.kt` | HTTPS-адрес, Retrofit, OkHttp и таймауты |
| `data/repository/NetworkTrackRepository.kt` | IO-диспетчер, сетевые ответы и обработка ошибок |
| `di/AppContainer.kt` | Сборка зависимостей и UseCase; в приложении используется сетевой репозиторий |
| `ui/catalog/CatalogViewModel.kt` | Загрузка/поиск/повтор, отмена предыдущего поиска, StateFlow |
| `ui/details/TrackDetailsViewModel.kt` | Загрузка и повтор деталей по аргументу навигации |
| `ui/components/NetworkStateContent.kt` | Общие состояния загрузки и ошибки |

Старый путь `data/repository/TrackRepository.kt` сохранён как `typealias` на доменный контракт. Это позволяет применить обновление обычной распаковкой без ручного удаления файлов. `MockTracks` и `MockTrackRepository` используются только тестами; `MainActivity` подключает сетевой источник через `AppContainer`.

## Как показать ошибку в записи

1. Запустить приложение с интернетом и дождаться списка.
2. Выключить Wi-Fi и мобильные данные **на телефоне/эмуляторе, где работает приложение**. Если на эмуляторе есть несколько доступных подключений, отключить их все.
3. Нажать обновление в каталоге или открыть карточку, чтобы действительно запустить новый запрос.
4. Показать индикатор загрузки, затем сообщение об ошибке. Максимальное время одного вызова ограничено 20 секундами.
5. Включить интернет и нажать «Повторить». Показать, что список/детали снова загружаются.

Простое отключение сети уже после успешной загрузки не убирает готовый список: для демонстрации ошибки нужно отправить новый запрос.

## Как получить скрин запросов для сдачи

Для встроенного Network Inspector выбрать эмулятор/устройство с Android 8.0 / API 26 или выше.

1. Запустить debug-сборку из Android Studio.
2. Открыть **View → Tool Windows → App Inspection**.
3. Выбрать запущенный процесс `com.example.itunes_search` и вкладку **Network Inspector**.
4. В приложении нажать обновление или выполнить поиск; затем открыть карточку.
5. Найти запросы к `itunes.apple.com` с путями `/search` и `/lookup`.
6. Нажать на запрос и открыть Request/Response, чтобы были видны параметры и JSON ответа.
7. Сделать скриншот этого окна и приложить его к сдаче отдельно или показать в записи.

Retrofit использует OkHttp, который поддерживается Network Inspector. Chucker и отдельный сниффер для выполнения этого требования не нужны.


Добавлены тесты:

- `NetworkTrackRepositoryTest`: реальные HTTP-запросы к локальному MockWebServer, query-параметры и их кодирование, поиск/lookup, HTTP-ошибки, неверный ответ, таймаут и отмена.
- `CatalogViewModelTest`: загрузка → результат, ошибка → повтор, ручная отправка поиска, пустой ввод, отмена старого запроса.
- `TrackDetailsViewModelTest`: ID из навигации, загрузка деталей, ошибка/повтор, отсутствие ID.
- `AppNavigationTest`: сохранённая навигация, отправка поиска, пустой результат и видимые состояния загрузки/ошибки. Тест использует отдельный моковый источник, чтобы результат не зависел от каталога Apple.
- Существующий `MockTrackRepositoryTest` адаптирован к новому асинхронному контракту. Тесты форматирования из Practice3 сохранены.

В среде подготовки статически проверены ресурсы, зависимости, слои и состав архива.
